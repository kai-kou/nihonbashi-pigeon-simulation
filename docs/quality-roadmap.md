# 品質向上ロードマップ

2026-10-31 制定。所有者指示（2026-10-31）「ロードマップ、エピック、Issue化して完遂するまで進める」に基づき、品質向上提案（専門チーム検討、2026-10-31）を実施計画化したもの。提案の根拠と各項目の詳細は提案書が正本であり、本書は実施の順序・完了条件・判断前提を定める。

## 目的

現行ビルド（単一 HTML）の品質を、計測に基づく完了条件付きで段階的に引き上げる。伸ばしどころは解像度ではなく次の3点である。

1. 質感チャネル: 街も鳩も拡散色のみで、normalMap／roughnessMap 等の質感チャネルが皆無であり、環境反射もない。手続き生成の補助マップと環境光で最も広い面積の質感を上げる。
2. 鳩の模様の実体化: モーフは色替え止まりで模様が描かれていない。模様の実体化と実在比率への配分変更で、路面視点の群れの情報量を上げる。
3. 遠距離 LOD: 建物は単一メッシュ化済みで、性能の支配項は鳩のドローコールである。遠距離の鳩を「細部を捨てて識別子を誇張した姿」に切り替える LOD で、性能と品質を同時に上げる。

PLATEAU への差し替えは主軸にしない。実測では道頓堀周辺の LOD2 は18%、外壁テクスチャはミナミに存在しなかったため、事前確認をゲートとする部分試行としてフェーズ3に置く。

## 判断前提（提案の判断分岐 D1〜D6 の固定）

実施を止めないため、分岐は次の前提で固定する。前提を覆す事情が計測で判明した場合のみ、Issue に記録したうえで所有者へ上げる。

- D1（項目7閉鎖の再開可否）: 再開しない。2026-10-31 に観察条件の限界として閉鎖した左右交互ステップの件には触れず、歩行の読み向上を目的とする変更は行わない。一般の LOD 工事の副次的改善まで禁じるものではない。
- D2（PLATEAU 試行）: フェーズ3で事前確認（対象メッシュの LOD2 棟数・比率とテクスチャ有無の実測）を行い、通過した場合のみ小エリアで部分試行する。全域置換はしない。本線は OSM の改善とする。
- D3（性能予算不足時の優先順位）: 街側の C1／C2 を優先し、翼の2関節化（P3）を繰り延べる。P3 は予算ゲート付きでフェーズ2の最後に置く。
- D4（Three.js 移行）: 品質工事は現行 r128 のまま進める。世代移行は見た目ゼロ変更を完了条件とする単独工程としてフェーズ3に分離し、品質変更と混ぜない。
- D5（配布・ソース形態）: 成果物の単一 HTML は維持する。ソース分割＋ビルド生成の二本立てはフェーズ3で検討・実施する。
- D6（PBR 用テクスチャの調達）: 手続き生成のみとする。写真ベース素材は使わず、出典・ライセンス確認を新規に発生させない。

## フェーズ

### フェーズ1: 計測と性能捻出＋低コスト品質

内容: B1〜B6（計測基盤、検証基準セット、マテリアル共有化、小物の Instancing、影のスロットリング、起動の軽量化）、遠距離 LOD の2層共同仕様の策定（P2-spec）、低コスト品質の同梱（P1 モーフ模様、P5 bump 転用、P4 飛行フラッシュ）。

遠距離 LOD の2層共同仕様は docs/far-lod-spec.md に固定した（Issue #14）。フェーズ2の P2 実装（#20）は同仕様を入力とする。

完了条件: ベースライン計測値が文書として記録され、フェーズ2の性能上限が実測から数値で固定されていること。検証基準セットで既確認9項目に退行がないことを、監査とは別の実ブラウザ経路で確認できていること。

### フェーズ2: 本丸の品質工事

内容: C1（ファサード PBR）＋C2（Sky＋PMREM）を対で、C3（近距離専用レイヤー）、C4（路面質感）、C5（屋上景観）、P2（遠距離 LOD 実装）、P6・P7・P8（至近と個体差）、P3（翼の2関節化、予算ゲート付きで最後）。

入口条件: フェーズ1の上限線が固定されていること。

完了条件: 各項目が指定視点（路面／川面／高架／至近）で実ブラウザ確認でき、確認／部分確認／未確認の処分が記録されていること。最悪ケース（全羽飛行時）を含む計測が上限線以内であること。

### フェーズ3: 大規模・個別判断項目

内容: C6（川面の限定平面反射）、C7（ポストプロセス、Ultra 限定）、P9（羽毛フリンジ試験、撤退条件付き）、X1（都市の空間チャンク化、フェード候補建物の除外線引き付き）、X2（Three.js 世代移行）、X3（PLATEAU 部分試行、事前確認ゲート付き）、X4（ソース分割＋ビルド生成）。

完了条件: 各項目が個別の完了条件を満たし、処分が記録されていること。ゲート不通過の項目は、実施しない判断とその根拠の記録をもって完了とする。

## 運用

- 各項目は有限単位の Issue として管理する（成果物・受入条件・証拠の置き場・担当・除外・停止条件を Issue 本文に明記）。
- 実装は作業ブランチと PR 経由とし、専門レビュー（実装者と異なる担当）を通してからマージする。
- 検証は監査ハーネスとは別の実ブラウザ経路を必須とし、「作ったが確認できない」状態を残さない。
- 進捗と検証結果は各 Issue と docs/improvement-log.md に記録する。
