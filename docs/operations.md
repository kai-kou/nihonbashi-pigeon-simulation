# Bolt 運用手順

リアリティ向上プログラム（docs/realism-roadmap.md）の実施手順の正本。ロードマップが計画と前提を示し、本書は1回の Bolt をどう進めるかを示す。進め方（AI-DLC + Bolt）の正本は docs/ai-dlc-bolt.md とし、本書と食い違う場合は docs/ai-dlc-bolt.md を優先する。検証基準は docs/verification-criteria.md、公開反映の手順は docs/build.md の同期手順 B を正とする。旧称はスプリント（第148回で閉鎖）。

## 基本姿勢

- 1 回の Bolt で進める有限単位（Unit of Work＝realism 子 Issue 1件）は 1 つだけとする。Bolt の種別は Inception／Baseline／Construction／Operations／Continuation の5種とする。
- Inception 退出チェック E1〜E7（docs/ai-dlc-bolt.md 第5節）を全て満たさない Unit は Construction に進まない。有限の成果物がない反復は Bolt として完了しない。同一条件の再確認だけの実行は Bolt に数えず、確認記録のみを残す。成果物が作れない回は、リファインメントを成果物として定義して実施する。
- WIP 上限: 未判定の PR と受入待ちの合計が2件に達したら、新規 Construction Bolt を開始せず Operations（検証）Bolt を優先する。
- 所有者への承認・確認は求めない（2026-11-02 所有者指示により承認不要化済み。docs/realism-roadmap.md の追加前提3）。所有者は Approver ではない。判断が割れる事項や進められない単位は、理由と次の手を Issue に記録して Bolt を止めず、次の単位へ進む。
- 費用・契約・権利に関わる外部送信、リポジトリ設定変更、削除は行わない。

## Bolt の進め方

### 1. 状態確認と単位の選択

- realism ラベルの open な子 Issue（Epic 自体は除く）を Epic 順（R0→R1→R2→R3→R4、同一 Epic 内は番号順）に並べ、open PR と Issue コメントを確認する。
- 前回 Bolt の PR が未マージで残っている単位があれば、新規単位に進まずその単位を継続する（重複着手禁止）。
- 対象単位の Issue に Bolt 着手コメント（開始時刻、この Bolt の範囲と完了条件、担当構成、Approver の明示）を記録して claim する。

### 2. 専門チーム組成

- 単位ごとに専門チームを組む。構成は Writer（実装担当）1名、専門レビュー担当 1 名（Writer と別セッションで、単位の専門＝外観／行動／環境・性能に合わせる）、QA 担当 1 名。Approver はコーディネーターとし、専門レビュー（実装 Approver）と QA（受入 Approver）の2段の独立判定を根拠に判定する。

### 3. ベースライン

- 対象領域の Before が docs/realism-scorecard.md に未記録なら、先に現行ビルドで計測・観察して記録する（Baseline Bolt として実施してよい）。改善の主張は Before／After の組でのみ行う。

### 4. 実装

- 作業ブランチは `bolt/<単位コード>-<短いslug>` とする。
- 実装後、tools/build.py で index.html を再生成する。静的計測（totalNodes／geometries／programs／textures の構造量、ファイルサイズ）を記録する。

### 5. PR とレビュー

- PR を作成し、本文に目的・変更内容・受入条件への対応見込みを書く。
- セルフレビュー（Writer 自身の差分レビュー）と専門レビュー・QA（別セッションの並行実施＝Mob Construction）を実施し、指摘は同 Bolt 内で修正してブラッシュアップする。
- QA はビルド成功と構造量・天井照合を PR に記録する。

### 6. Approver 判定とマージ

- Approver（コーディネーター）が Issue の受入条件を 1 件ずつ照合する。
- 計測可能な条件をすべて満たし、性能天井（docs/verification-criteria.md の 6 条件と構造上限）を 1 つも超えず、レビュー指摘が解消していればマージする（head を固定して照合する）。
- 実ブラウザ目視が要る視覚受入は、スコアカード検証バッチ（R0／R4）へ送る旨を PR と Issue に明記したうえで、計測可能な条件での実装受入をもってマージ可否を判断する。
- 条件を満たせなければマージせず、PR を開いたまま Issue にブロッカーと次の手を記録する。Approver は G1〜G4 の免除、性能天井の引き上げ、受入基準の事後変更による合格化を行わない。

### 7. 記録

- 結果を対象 Issue のコメントと docs/improvement-log.md（PR に含める）へ記録する。結果コメントには終了時刻、対応時間と枠（3時間）に対する利用率、判断ログの必須項目（docs/ai-dlc-bolt.md 第6.3節）を含める。

## 制約

- 前提 D1〜D6（docs/realism-roadmap.md）を継承する。
- 性能天井はリアリティのために引き上げない。超過する変更はマージしない。
- 性能予算が不足する場合は街側（R3）を優先し、翼・行動系の重い単位を繰り延べる（D3）。

## 公開反映

- 公開反映は docs/build.md の同期手順 B に従い、「反映→再共有→配信実測」の 3 点セットで確認する。配信版が現行ビルドへ切り替わったかは、ビルド識別子（計測パネルのセクション有無、export の識別マーカー等）で判定する。共有状態の読み戻しや公開 URL の不変だけでは、公開反映を確認したことにならない。
- 訪問者アクセスと管理操作を混同しない。公開ページは未ログイン訪問者でも開けるのが既定であり、画面の Log in／Sign up 表示はサイトの常設表示であって、アプリが非公開・アクセス不可である証拠ではない。アクセス可否は、未ログインでアプリ本体（シーンと計測パネル）が表示されるかで判定する。

## ブロッカーの扱い

- ブロッカーの前提は引き継ぎ時に再検証する。前回 Bolt のブロッカー文（「〜が必要」「〜できない」）を未検証のまま転記しない。前提が崩れた場合に予測される観測を 1 件書き、実際に試してからブロッカーを更新する。

## 報告の原則

- 報告はアウトカムベースとする（何が見て分かるように変わったか、受入条件ごとの判定、未達があれば理由と次の手、根拠となる PR・計測値）。
- 「完了」「解消」「一致」「成立」は、検証証拠（読み戻した SHA・PR 状態・計測実値）を同じ報告内に引用する場合にだけ使う。目視で確認できていない視覚受入は「未確認」と書く。件数を書く場合は内訳と分母を数字の直後に書く。
