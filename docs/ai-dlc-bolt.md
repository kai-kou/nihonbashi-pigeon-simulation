# AI-DLC + Bolt 進め方（日本橋ハトシミュレーション）

2026-11-11 制定。所有者指示（2026-11-11、添付レポートの精査と専門チームの検討を経た切替指示）に基づき、本プロジェクトの開発スタイルを AI-DLC（AI-Driven Development Life Cycle）+ Bolt へ切り替える。本書は「どう進めるか」の正本である。「何を作るか」の正本は docs/realism-roadmap.md のままとし、受入の物差しは docs/verification-criteria.md のままとする。本書は両文書を変更しない。

## 1. 目的と適用範囲

- 対象はリアリティ向上プログラム（Epic #82）の全 Unit である。
- 実行基盤は変更しない。cron `pigeon-realism-sprint`（3時間ごと、timeout 3600秒）が1回に有限単位を1つだけ進める現行の cadence をそのまま Bolt の枠とする。
- 切替の実質は名称の変更ではなく、次の3点である。(1) Inception 退出チェック（第5節 E1〜E7）の明文化、(2) Bolt の完了規律（第4.3節。有限の成果物がない反復は Bolt として完了しない）、(3) KPI による効果測定（第8節）。
- 過去のスプリント記録・Issue・PR・ブランチ名は改名しない。移行表記は第9節に従う。
- 本書の適用は本プロジェクト（日本橋ハトシミュレーション）のみである。他プロジェクトの一般スプリント運用は改名しない。

## 2. 用語対応

| AI-DLC 用語 | 本プロジェクトでの実体 |
|---|---|
| Intent | ロードマップ（docs/realism-roadmap.md）の目的と所有者指示。Intent は roadmap を指し、単独の新文書は作らない |
| Unit of Work | realism 子 Issue 1件（Rコード付き有限単位）。Rコードと Issue 番号は不変 |
| Bolt | cron 1回の実行（3時間枠）で Unit を1つ進める最小の反復。旧称スプリント |
| Mob Elaboration | 専門監査＋リファインメントの並行実施と、結果の Issue への統合記録。同期会議ではなく非同期モブとして実施する |
| Mob Construction | Bolt 内での専門レビュー＋QA の並行実施。実装と並行して同一 PR 上で動き、指摘を同一 Bolt 内で解消する |
| Operations | マージ後の記録と公開反映の配信確定。R4-2 等の公開反映を伴う単位では、edit → share → 配信実測の3点セットが完了条件となる |
| Approver | コーディネーター（第6節）。所有者は Approver ではない |

Epic は Unit の束として扱い、Bolt の対象にはしない。子 Issue が複数 Bolt にまたがる場合は、同じ Unit に対する継続 Bolt として扱い、Bolt ごとに「この Bolt で進める範囲と完了条件」を claim コメントに明記する。

## 3. フェーズ定義

### 3.1 Inception（Mob Elaboration）

- 入口: 対象 Unit の選定（open 子 Issue の Epic 順、未マージ PR の単位の継続優先、重複着手の禁止）。
- 活動: 専門監査とリファインメントの並行実施、受入条件・リスク・非機能条件の精緻化、退出チェック（第5節）の実施。
- 出口: 第5節 E1〜E7 を全て満たすこと。満たさない Unit は Construction に進まない。
- バックログ（実行可能な ready な Issue）が枯渇している場合は、その Bolt 内でリファインメントを実施し、整備した Issue と新たに ready にした単位を成果物とする（Inception Bolt、第4.1節）。

### 3.2 Construction（Mob Construction）

- 入口: Inception 退出チェックを通過した Unit であること。WIP 上限（第7節）に達していないこと。
- 活動: 実装（作業ブランチ、新規ブランチは `bolt/` 接頭辞）→ PR 作成 → セルフレビュー → 専門レビューと QA の並行実施 → 指摘の修正 → Approver 判定（受入条件の1件ずつの照合、性能天井の照合）。
- 出口: PR がマージされるか、マージしない場合はブロッカーと次の手が、前提を再検証した結果とともに Issue に記録されていること。

### 3.3 Operations

- 通常単位の Operations は、マージ結果の記録、Issue への結果コメント、docs/improvement-log.md とスプリントログへの記録、定時報告への集約とする。
- 公開反映を伴う単位では、edit → share → 配信実測の3点セットを完了条件とし、配信版の切り替わりはビルド識別子で判定する。share の成否や URL の不変を証拠に使わない。公開反映の判定には G4（スクリーンショット目視必須）が適用される。

## 4. Bolt

### 4.1 Bolt の種別（5種）

| 種別 | 目的 | 成果物 |
|---|---|---|
| Inception | Intent の固定、Unit 分解、退出チェックの実施。リファインメントを含む | ready な Issue 群と退出チェック結果 |
| Baseline | Before の計測・観察とスコアカードへの記録 | Before の計測値と処分 |
| Construction | 実装、PR、レビュー、QA、マージ | PR とマージ結果、計測値と天井照合 |
| Operations | マージ済み成果の配信確定・検証 | 配信実測の証拠（ビルド識別子、スクリーンショット目視） |
| Continuation | 未完了 Unit の継続 | 新規の証拠か判断材料。同一条件の再確認だけでは成立しない（第4.3節） |

### 4.2 時間枠と並列可否

- 枠は3時間（cron の実行間隔）。対応時間（claim から結果の記録完了まで、PR マージ時はマージと記録完了まで）を実測し、枠利用率を記録する。
- 対応時間が90分未満（枠の半分未満）の Bolt は「短時間」とし、プランニングの振り返りと改善（次回選ぶ Unit と見積り）を報告に含める。
- Bolt 同士は並列実行しない。常に1 Bolt だけが進行中であり、前 Bolt の PR が未マージの Unit がある場合はその Unit の継続を優先する。並列が許されるのは Bolt 内部のレビュー・QA と、読み取り専用の監査・計測だけである。

### 4.3 Bolt の完了規律（完了条件）

次の全てを満たしたときに Bolt は完了とする。

1. claim コメント（開始時刻、対象 Unit、この Bolt の範囲と完了条件、担当構成、Approver の明示）が Issue に記録されている。
2. 種別ごとの有限の成果物が存在する。**有限の成果物がない反復は Bolt として完了しない。同一条件の再確認だけの実行は Bolt に数えず、確認記録のみを残す。成果物が作れない回は、リファインメントを成果物として定義して実施する。**
3. マージ判定が記録されている。マージした場合は受入条件の1件ずつの照合結果と性能天井の照合値が証拠として残っている。マージしない場合はブロッカーが、前提を再検証した結果とともに記録されている。
4. 結果コメント（終了時刻を含む）が Issue に記録され、スプリントログへの記録が完了している。対応時間と枠利用率が算出できる状態であること。
5. 視覚受入が関わる場合、その状態が実態どおり（未確認、検証バッチ送り等）に明記されている。Operations の証拠はビルド識別子と配信実測に基づくこと。

Unit の完了（クローズまたは受入）は Bolt の完了とは別に判定し、消化した Issue 数は「クローズまたは受入に至った件数」で数える。判断ログの必須項目が揃わない Bolt は未完了とする（第6.3節）。

## 5. Inception 退出チェックリスト（E1〜E7、全て必須）

新しい Unit を Construction の対象にする前に、次を全て確認し、結果を Epic または対象 Issue に記録する。1つでも欠ける Unit は Construction に進まない。

| ID | 項目 | 内容 |
|---|---|---|
| E1 | 受入条件の定め方（4点）と受け入れテストの事前固定 | 受入条件を1件ずつ列挙し、各条件に (1) 指定視点、(2) 距離条件、(3) 「確認」の基準（要素単位の列挙、部分確認と未確認の定義）、(4) 性能条件（最悪ケースを含む計測と天井との照合方法。性能に影響しない単位は「性能影響なし」と理由）を付ける。少なくとも1件の受け入れテスト（決定論的テストまたは再現可能な視覚判定手順）を実装前に作成し、Approver（実装）が検証して凍結する。実装後に基準を書き換える場合は再検証と変更理由の記録を必須とし、過去の不合格を事後的に合格化しない。Intent と Unit の確定（目的、成果物、除外、停止条件の Issue への明記）を含む |
| E2 | ゲート適用宣言 | G1〜G4 のどれがこの Unit に適用されるかを宣言する。対応は次のとおり。G1 シェーダ照合: シェーダ文字列を新規作成・置き換えする単位（実装受入の前、未解決0件が条件）。G2 コンソールエラー帰属: 全 Unit（エラーが観測された場合に発動し、帰属記録まで実装受入としない）。G3 視覚繰り延べ制限: 外観を変える Unit（同一描画領域の視覚未確認がある間は後続をマージしない）。G4 配信実測の目視: 公開反映を含む Unit（3点セットの判定条件）。宣言漏れは退出不可 |
| E3 | 計測系条件の実行可能性確認 | 計測で判定する条件は、判定に使う手段が現行ビルドで実行可能であることを、実際に1回試して確認していること。UI で作れない観測条件は、その時点で受入条件として成立しない |
| E4 | Approver の事前指名 | Writer、Approver（実装）、Approver（受入）を claim 時点で記録する（第6節の分離条件を満たすこと）。実装が終わってからレビュー者を探す運用は行わない |
| E5 | 非機能条件（性能天井を含む） | 性能天井（docs/verification-criteria.md の6条件と構造上限。totalNodes 4046、programs 45、geometries 683、textures 88、usedJSHeapSizeMB 102 等）の残量を確認し、Unit の増分見積もりが残量に収まること。D1〜D6 と G1〜G4 に抵触する Unit が含まれていないこと |
| E6 | Before の存在または Baseline Bolt の計画 | Before がスコアカード等に記録されていること。記録がない単位は、最初の Bolt を Baseline Bolt（Before 記録専用）とすることが決まっていること |
| E7 | リスクと除外の明記 | 依存、未確定の前提、失敗時の戻し方、対象外とする事項を書く。未確定の前提に依存する単位は、前提が解けるまで ready にしない |

## 6. Approver と役割

### 6.1 役割定義

| 役割 | 担い手 | 責務 |
|---|---|---|
| Prompter / Writer | 実装担当 | Intent の入力、コード変更、PR 作成、証拠の提出。自分の Unit の合否判定とマージ判定は行わない |
| Approver | コーディネーター | Bolt の合否とマージ可否の最終判定。判定は下記2段の独立判定を根拠にする |
| Approver（実装） | 専門レビュー担当。Writer とは別のエージェントかつ別セッション | 設計と差分のレビュー、G1・G2 の照合結果の確認、性能増分の累積確認、合否と理由の記録。対象 Unit のコードを編集した場合は Approver を交代する |
| Approver（受入） | QA 担当。Writer および実装 Approver とは別セッション | 受け入れテストの実施と処分（確認／部分確認／未確認）、G3・G4 の判定、公開実測の目視 |

- Approver は claim 時に明示する。所有者は Approver ではない。所有者への承認・確認は求めない運用（承認不要化、2026-11-02 所有者指示）は維持する。
- 小規模な文書のみの単位などでは、実装 Approver と受入 Approver の兼務を許す。ただし Writer との兼務はいかなる単位でも許さない。兼務した場合は判断ログにその旨と理由を書く。
- 同一ペア（Writer と Approver の固定組み合わせ）が3 Bolt 連続しないよう、レビューの時点で組み合わせを点検する。

### 6.2 Approver の権限の上限

- Approver は G1〜G4 の免除、性能天井の引き上げ、受入基準の事後変更による合格化を行えない。ゲートに抵触した場合は不合格として差し戻すか、判断を所有者へ上げるかの二択とする。
- 方針の大きな変更（ロードマップの目的変更、性能天井の変更、検証基準自体の変更）とコスト発生は Approver でも決められず、従来どおり所有者へ上げる。

### 6.3 判断ログ

各 Bolt の完了条件に、対象 Issue への判断ログ記録を含める。記録項目は、Unit ID と Bolt 番号、Intent の1行要約、Writer、Approver（実装／受入）、主要な設計決定とその理由、却下した代替案とその理由、適用したゲート（G1〜G4 の該当有無）、合否と処分、留保（未確認事項とその次の手）、性能増分（構造量の前後値）、所有者へ上げた事項の有無とする。判断ログは新しい台帳を作らず、Issue コメントと PR を正本とし、スプリントログへは索引（コメント ID）だけを残す。必須項目が揃わない Bolt は未完了とする。

## 7. WIP 上限と領域ロック

- 未判定の PR と受入待ちの合計が初期値2件に達したら、新規の Construction Bolt を開始せず、Operations（検証）Bolt を優先する。これは開始の停止であり、進行中 Unit の中断ではない。上限はベースライン期間（第8節）後に見直す。
- G3 の同一描画領域ロックは Inception 時点から効かせる。同一描画領域の視覚未確認がある Unit は、E2 の宣言時点でその領域の後続 Unit を開始不可とする。

## 8. KPI

### 8.1 測定原則

- アウトカムを測り、活動量を測らない。指標は全て Issue・PR・スプリントログの既存記録から集計できるものに限る。
- 移行後最初の10 Bolt はベースライン期間とし、目標値は置かず実測分布だけを取る。その後に閾値（WIP 上限、視覚滞留の最大値等）を確定する。ベンダーが公表する加速倍率（10〜15倍等）は目標に使わない。
- 速度指標と品質指標は常に対で読み、片方の改善が片方の悪化で買われていないかを確認する。

### 8.2 測定する指標

| 指標 | 定義 |
|---|---|
| Bolt リードタイム | claim コメント時刻から結果コメント（受入判定込み）の記録完了までの経過時間。中央値と90パーセンタイルで集計 |
| 配信確定までのリードタイム | マージ時刻から、公開反映の配信実測（G4）通過までの時間。公開反映頻度（週あたりの G4 通過回数）と併記する |
| 手戻り率 | 専門レビューまたは QA で差し戻し（修正要求）を受けた PR 数／全 PR 数と、受入未達で Continuation Bolt になった割合の2本立て |
| 受入差し戻し率 | 受入判定で不合格となった Unit 数／受入判定を行った Unit 数。実装受入と視覚受入で分けて集計する |
| 視覚受入の滞留 | 実装受入済みだが視覚未確認の Unit の滞留日数（中央値と最大値）と、未確認の描画領域の数 |
| ゲート抵触件数 | Bolt あたりの G1 未解決件数、帰属未確定のコンソールエラー件数、性能天井の超過件数。いずれも常時0を目標とし、率ではなく件数で扱う |
| 性能天井の余裕度 | 構造量5項目それぞれの上限に対する使用率の最大値（パーセント） |
| 判断ログ完全率 | 必須項目が揃った判断ログの Bolt 数／全 Bolt 数。目標100パーセント |

DORA 4指標との対応は次のとおり。デプロイ頻度＝公開反映頻度（G4 通過ベース）、変更のリードタイム＝Bolt リードタイム、変更失敗率＝受入差し戻し率と公開反映の失敗の合算、復旧時間＝不合格・退行の検出から修正のマージと再受入までの時間。

### 8.3 測らない指標

コード量（追加行数、変更ファイル数）、PR 数、ストーリーポイント、AI 生成量（生成トークン、生成コード行数）は生産性の指標に使わない。消化の単位は受入を通過した Unit 数で数える。

## 9. 移行表記

- スプリントは第148回で閉じる。移行後の実行は「Bolt 第N回（通し第M回）」と二重表記する（初回は Bolt 第1回（通し第149回））。
- スプリントログのファイル名（realism-sprint-log.md）と既存の見出しは変更しない。移行の境目に移行記録の節を1つ挿入し、以後は Bolt の見出しで追記する。
- 新規ブランチは `bolt/` 接頭辞を使う。既存ブランチは変更しない。
- 進捗率（実装進捗率・完全完了率）の定義は変更しない。Bolt 化は率の計算に影響しない。
- 初回 Bolt は、移行 PR のマージ後の次回 cron 実行からとする。

## 10. 導入しないもの・変更しないもの

- 導入しない: 所有者の人間承認ゲートの復活、複数 Bolt の並列実行、AWS ツールチェーン（Kiro、Amazon Q Developer、Bedrock AgentCore、awslabs/aidlc-workflows 等）の導入（コスト発生事項として所有者判断に分離する）、ベンダー効果数値の目標化、過去のスプリント記録・Issue・PR・ブランチ名の改名、他プロジェクトの一般スプリント運用の改名。
- 変更しない: 性能天井、D1〜D6、検証ゲート G1〜G4、docs/verification-criteria.md の本文、検証基準の数値。方法論の切り替えは進め方の変更であり、固定前提の変更ではない。
- 新規の描画サブシステムを伴う Unit では、最初の Bolt で最小構成の通し確認（Walking Skeleton に相当）を行う。

## 11. 停止条件

次のいずれかに当たった場合、その Bolt は停止し、理由と次の手を Issue に記録する。

1. E1〜E7 のいずれかが未充足のまま Construction の開始を求められる場合。
2. G1 の未解決が0件にならない、または帰属未確定のコンソールエラーが残る場合。
3. 性能天井を超過し、天井内で収める修正の見通しがない場合（天井の引き上げは解消手段にしない）。
4. 同一描画領域の視覚未確認があり、G3 により後続に進めない場合。
5. 方針の大きな変更またはコスト発生が必要と判明した場合（所有者へ上げる）。
6. WIP 上限（第7節）に達し、レビューと受入の在庫が消化できない場合。
