## 2. 生成（tools/build-citygeo-hero.py）

入力は上記の合体 JSON。出力は `window.CITYGEO_HERO = { pos, counts }` で、
形式は現行 `src/data/citygeo.js`（`window.CITYGEO`）と同一（base64 の
Int16 dm pos + Uint32 counts）。建物は中間 JSON の順序のまま出し、`counts`
は建物ごとに 1 件。

### 2.1 生成規則

- 非 LOD2 棟（643 棟）: 現行と同じ押し出し。壁を先に 2 三角形 × フットプリント
  辺数（6n 頂点）、屋根を earcut 三角分割（n−2 三角形、ただし重複点を除く
  14 棟は §2.4 参照）。壁の巻き方向はフットプリントの符号付き面積で決め、
  外向きになる（現行データ 9,079 棟に対する独立検証は §2.3 参照）。
- LOD2 棟（800 棟）: 保持する lod2Solid 面を扇状分割（面あたり n−2 三角形）。
  巻き方向は GML のリング順のまま（根拠は §2.5）。
- pos の三つ組は (x_dm, y_abs_dm, −north_dm)。y は baseZ を加算した絶対標高。
  Int16 の範囲内であることを生成時に検査している（ヒーロー圏の実測は §2.2）。

### 2.3 屋根三角分割の同一性（build-city.js 読解の結論）

`src/scripts/build-city.js` の `buildCity()` は `window.CITYGEO.pos`
（Int16 dm base64）と `counts`（建物ごとの頂点数）を読み、pos を /10 で m 化
したうえで法線・色・uv・aBld を位置から再計算する。建物ごとの処理は
`CITY.buildings`（フットプリント・高さ）から行い、`counts[bi]` はその建物の
頂点数としてのみ使う。壁・屋根の色分けは「建物範囲の先頭 6n 頂点が壁、残りが
屋根」という位置の規則で決まる（n はフットプリント点数）。uv の分岐は法線に
よる（ny>0.7 なら屋根テクセル、 else 壁 uv）。

- 屋根三角分割の実体: 現行 citygeo.js の屋根は three.js r128 の
  `THREE.ShapeUtils.triangulateShape`（Earcut）で、フットプリントを
  (x, north) 座標で三角分割したもの。現行 9,079 棟の全屋根について、
  three.js の出力と現行データの屋根三角形を比較したところ、順序まで含めて
  9,077/9,079 棟が一致した。残る 2 棟（bi 621・8649）は複雑な凹多角形で
  ear の切り方が異なるだけで、三角形数・被覆は同一である。
  （この 2 棟は、現行データ自体が r128 earcut と一致しない既存の差分であり、
  本生成器の問題ではない。）
- 本生成器は earcut を Python へ忠実に移植した。移植版と three.js r128 の
  出力を現行 9,079 棟の全フットプリントで比較し、順序まで含めて
  9,079/9,079 棟が一致した（三角形 26,920 件）。ヒーロー圏の LOD1 643 棟に
  ついても three.js と 643/643 棟が一致した。
  なおヒーロー圏の earcut 参照ファイル（`earcut-hero-lod1-ref.json`）は
  三角形数のみを保持しており（643 件・合計 2,473）、保存されたファイル
  単体では数レベルの一致しか示さない。順序までの一致は次の推移で裏付ける:
  (a) 移植版 earcut と three.js r128 は現行 9,079 棟の全フットプリントで
  順序まで含めて一致した（上記）。(b) 専門レビューが移植版を独立に再実行し、
  現行 9,079 棟で参照出力と順序まで含めて 9,079/9,079 棟が一致することと、
  ヒーロー圏 LOD1 643 棟の生成済み屋根が移植版出力と 643/643 棟で一致する
  ことを確認した。(a)+(b) により、ヒーロー圏の屋根は three.js の出力と
  順序まで一致する。
- 壁の巻き方向の規則（符号付き面積の符号で 2 パターンを切り替える）は、
  現行データに対する独立検証（レイキャストによる外向き判定）で
  9,079/9,079 棟が一致した。ただし現行データ自体はこの規則から先頭辺が
  異なる 48 棟（0.53%）があり、その 48 棟の壁は先頭辺の比較では内向きと
  判定される（レイキャストでも確認済み）。全辺で見ると 1,015 棟に規則外の
  辺がある（例: bi 5 は 32 辺が規則通り・17 辺が逆向き、bi 0 は 1 辺が
  逆向き）ため、「48 棟の壁は内向き」という記述は言い過ぎであり、本記録
  では「先頭辺が規則と異なる 48 棟」と書き換えた（専門レビュー提案1）。
  現行の街マテリアルは FrontSide（既定）のため、その 48 棟の壁は
  外側から見えない既存の不具合である。本生成器は正しい規則を使うため、
  ヒーロー圏ではこの不具合を継承しない。現行データ側の修正は本 Bolt の
  範囲外（#140 への申し送りではなく、別途の判断事項として記録する）。

### 2.5 LOD2 面の向き（巻き方向）の決定

GML リングの向きをそのまま使う。根拠は符号付き体積（発散定理）による検証:

- 保持面＋Ground 面（raw の向き）で 800 棟の符号付き体積を合計すると
  8,268,573,112 dm³（8.27e9）で、798/800 棟が正の体積を持つ。
  Before（Bolt 第4回）は 8,260,077,897 dm³、799/800 棟が正。
  合計・棟数の変化は、符号付き体積が原点に依存する計量であることによる
  （下記の「体積値の原点依存性」を参照）。建物の形状自体は緯度経度で
  不変であり（§6）、反転しないという決定は変わらない。
  反転ヒューリスティクスの比較値（2,415,009,187 dm³・5,237,995,657 dm³）は
  旧原点での値で、raw との差は 3 倍以上あり、+0.1% 程度の原点依存の
  変動では順位は変わらないため再計算しない。
- 比較のため 2 通りの反転ヒューリスティクスを試した:
  フットプリント重心による判定で反転すると合計 2,415,009,187 dm³（679 棟が正）、
  レイキャストによるプローブ判定で反転すると合計 5,237,995,657 dm³（720 棟が正）。
  どちらも raw より悪化するため、反転しないことを採用した。
- 反転ヒューリスティクスが誤る理由: フットプリント重心は LOD2 ソリッドの
  中心を表さない（重心がソリッドの外にある建物が 37 棟、傾斜屋根では法線の
  水平成分が判定を狂わせる）。レイキャストのプローブは、非平面・凹面では
  面の重心が面の表面上にないため、面の外側 1 dm のはずの点がソリッドの
  内側に入ることがある。
- 例外 2 棟: 建物 index 1148（h 81 dm、フットプリント 8 点、面積 2,191.5 dm²）。
  raw の符号付き体積は −784,646 dm³（Before は −186,100 dm³）で、
  面積×高さの概算 +177,500 dm³ とほぼ符号だけが逆の値になる。面ごとの
  寄与も正負が大きく混在しており、ソースデータ側でソリッドが反転して
  いるか、複雑な屋根で面が重なっている疑いがある。本 Bolt では修復せず、
  raw のまま出す。#140 の視覚確認でこの 1 棟の描画を確認すること。
  建物 index 1300（h 104 dm、フットプリント 4 点、面積 3,548.5 dm²）も
  原点統一後に負になった（保持面＋Ground 面で −525,524 dm³、Before は
  +240,818 dm³）。旧データを原点シフト分だけ平行移動して再計算すると
  −476,203 dm³ になり、新しい値に近い。すなわち 1300 の符号反転は
  形状の変化ではなく体積計量の原点依存性によるもので、1148 とは
  原因が異なる。1148 と同じく修復せず、#140 の視覚確認で描画を確認すること。
- 体積値の原点依存性（Bolt 第6回で確認）: 符号付き体積は、面集合が
  閉じたソリッドをなす場合にのみ原点の平行移動で不変になる。
  LOD2 の保持面＋Ground 面は Floor／Closure 面を含まず、個々の建物でも
  面が閉じていないものがあるため、原点の平行移動で値が変わる。
  旧データを原点シフト（東 +18,699 dm・北 +22,758 dm）だけ平行移動して
  再計算すると、保持面のみの合計は 9,233,635,052 dm³（新しい値
  9,235,615,172 dm³ に近い）、保持面＋Ground 面の合計は
  8,266,828,920 dm³（新しい値 8,268,573,112 dm³ に近い）になる。
  残差は dm への再丸めと M_LON の再評価によるものである。
  したがって体積値の変化（+0.1% 程度）はデータの変化ではなく計量の
  原点依存性であり、巻き方向の決定（反転しない）には影響しない。

### 2.6 フットプリントの重複点

## 4. #140 への申し送り（描画への統合時に必要なこと）

1. **CITY_HERO 配列が要る**: `counts` の順序は中間 JSON の `buildings` の
   順序と同一。`buildCity()` は `CITY.buildings` を走査して `counts[bi]` を
   引くため、#140 ではフットプリント・高さ・baseZ を持つ
   `window.CITY_HERO`（buildings 1,443 件、同一順序）を作ること。
   中間 JSON の `buildings` は `[h_dm, usage, footprint, lod2_index, baseZ_dm]`
   の形式で、そのまま CITY 互換である。
2. **壁・屋根の色分けは位置規則**: 先頭 6n 頂点が壁色（cWall）、残りが屋根色
   （cTop）。LOD2 棟では先頭 6n 頂点は GML の面順の扇状分割であり、壁面の
   頂点数が 6n と一致するとは限らない。そのため LOD2 棟では、6n の内側に
   入った屋根面が壁色に、6n を超えた壁面が屋根色になる。uv の分岐は
   法線による（ny>0.7 が屋根）ためテクスチャ写像には影響しないが、平色の
   違いは出る。対応案: (a) プレビューでは近似のまま許容する、(b) 色分けも
   法線基準（ny>0.7 → cTop）に変える（uv 分岐と整合する最小の変更だが、
   現行の街の描画も変わるため前後比較が要る）、(c) 頂点ごとに面種を持つ
   チャンネルを追加する。推奨は (b) の検討だが、決定は #140 で行うこと。
3. **高さのある側の付帯物**: `rooftopItems`（y=h）、`perchPoints`
   （y=h+0.02）、`ledgePoints`（y=min(3.2, h−0.4)）は地面を 0 と仮定して
   いる。ヒーロー圏では baseZ を加算すること（y=baseZ+h 等）。加算しないと
   高台の建物の屋上付帯物・止まり木が地中に埋まる。
4. **C7 の AO グラデーション**: 地面 0〜4.5 m で暗くする処理は絶対高さ
   `position.y` で駆動するため、baseZ の高い建物では 1.0 に飽和する
   （暗い基部が出ない）。見た目の差は小さいが、#140 で確認すること。
5. **ファサード uv は世界座標基準**（u・v とも fract）のため、ヒーロー圏の
   座標でもそのまま使える。v は baseZ でずれるが fract のため影響しない。
6. **重複点の扱い**（§2.6）: hero CITY を作るとき、フットプリントの連続
   重複点を除去する場合は n が変わるため壁の 6n 規則との整合に注意すること。
   除去しない場合は壁に面積ゼロの三角形が残るが無害である。
7. **建物 1148・1300 の確認**（§2.5）: ソースデータ側の異常の疑いがある
   1148 と、体積計量の原点依存性で負になった 1300 の 2 棟。
   プレビューの視覚確認で描画を確認すること。
8. **本データに含まれないもの**: 道路・水面・ラベル（#147）、地形メッシュ
   （#148）、テクスチャアトラス（#140 の第 2 段階）、出現位置・初期視点
   （#141）。ヒーロー圏の三角形数は 52,941 で現行の街全体 117,076 より
   少ないが、これは 2 メッシュ分だけの値であり、全域への置き換え時の
   性能は #149 の試算で扱うこと。
9. **現行データの先頭辺が規則と異なる 48 棟**（§2.3）: ヒーロー圏では発生しない。
   現行の街全体をヒーロー圏へ置き換える際は、この不具合は解消される。
   現行 citygeo.js 自体の修正は本 Bolt の範囲外。
