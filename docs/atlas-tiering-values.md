## 1. 対象と方法

### 1.1 入力

- 配置表 `src/data/texture-atlas-layout.json`（main、sha 03722203…、299,379 bytes、800 件。各ファイルに orig_w・orig_h・path・jpeg_bytes（長辺 128・q85 での再エンコード実測値）付き）。meta の pixel_area は 7,841,792 px、tile_jpeg_bytes_total は 2,136,700 bytes。
- PLATEAU 抽出 GML（`hidden_files/plateau-relocation/gml/` の 52350421_bldg.gml・52350422_bldg.gml）。建物ごとの measuredHeight・usage・フットプリント（lod0FootPrint、無ければ lod0RoofEdge）を抽出し、配置表の path に含まれる建物（appearance ディレクトリ名）と突き合わせた。
- 寸法・再エンコード実測（Bolt 10 の 21 ファイルサンプル。`hidden_files/bolt10/tex-hero-sample-result.json`・`tex-hero-sample-variants.json`）。JPEG 推定の較正に使った。

### 1.2 配置面積の再計算（拡大なし規則）

`tools/build-texture-atlas.py` の reencode() と同一の規則で、元寸法から長辺 128・256・512 での配置寸法をファイルごとに計算した。元長辺が目標長辺以下のファイルは元寸法のまま（拡大しない）。寸法の丸めは `max(1, round(w * s))`（s = 目標長辺／元長辺）で、生成ツールと同一である。再計算スクリプトは `tools/atlas-tiering-values.py`（本 PR に含む。配置表と選定リストだけを入力とし、§9 の記録値をすべて assert で検証する）。

### 1.3 GML と配置表の突き合わせ

GML の `app:ParameterizedTexture`（imageURI と `app:target` の `uri` 属性）と、建物の `bldg:lod2Solid`・`bldg:boundedBy` 内のポリゴン id から、ファイル→建物の対応付けを行った。結果は 800 件すべてがちょうど 1 棟に結びつき、未対応 0 件・複数棟への対応 0 件であった。LOD2 建物 800 棟すべてがテクスチャを持ち、テクスチャを持つ建物はすべて LOD2 であった。ファイルと建物は 1 対 1（1 棟あたり 1 ファイル）である。フットプリント面積は lod0FootPrint（無ければ lod0RoofEdge）の posList（緯度・経度）から、原点 [34.6668, 135.5058]・m_per_deg [110934.496, 91656.759]（中間 JSON と同一）での平面換算＋ shoelace 公式で計算した。建物 1,443 棟すべてで高さ・フットプリントの欠損は 0 件であった。

### 1.4 シート枚数の模擬

`tools/build-texture-atlas.py` の shelf_pack() をそのまま再現した（高さ降順・幅降順・名前順にソートし、2px ガター付きでシェルフパッキングする。シート 4096px）。模擬であることを明記する。検証として長辺 128 での模擬は 1 枚・充填率 0.4674 となり、Bolt 11 の正確値（1 枚・0.4674）と完全一致した。

### 1.5 JPEG 容量の推定方法と不確かさ

ファイルごとの JPEG 推定は `jpeg_L = jpeg_128 × (area_L / area_128)^α`（α = 0.65）とした。jpeg_128 は配置表の実測値（全 800 件）で、面積比だけをモデルで伸ばす方式である。α は Bolt 10 の 21 ファイルサンプルから較正した（面積が伸びる 14 件での α の中央値 0.649、範囲 0.553〜0.769）。サンプルでの検証では α = 0.65 の予測は長辺 256 で実測比 −2.4%、長辺 512 で実測比 −8.6% であり、中央値はやや過小に出る傾向がある。感度として α = 0.55〜0.77 の範囲も併記する（母集団の合計は平均へ回帰するため、範囲は保守的な幅である）。アトラス JPEG はタイル JPEG 合計 × 1.04386 とした（Bolt 11 の正確値 2,230,406／2,136,700）。base64 は `(bytes + 2) // 3 * 4`（生成ツールと同一の式。Bolt 11 の正確値 2,230,406 bytes → 2,973,876 bytes と一致することを確認済み）。

採用しなかった方法: §10.2 の pooled 比率（orig 合計に対する比率 0.798 等）を全ファイルへ適用する方式は、サンプル 21 件の比率を 800 件へ外挿するもので、§10.3 の記録どおり巨大ファイルの有無に支配されるため却下した。参考までに pooled 比率での全 256 タイル JPEG は 7,745,922 bytes となり、α モデルの中央値 4,262,188 bytes と大きく乖離する（§10 の推定の幅の記録と整合する）。

## 5. 新しい上限値の提案

### 5.1 値・根拠・測定方法

- 値: ヒーロー圏アトラスの GPU 試算（読み方 (a)）の上限値 **130 MiB（136,314,880 bytes）**。対象はヒーロー圏（52350421 大手前＋52350422 大阪城公園、LOD2 800 棟）の階層化アトラス（S4 ミックス）のみとする。全域への例外拡大はしない。
- 根拠: S4 ミックスの実測値 (a) 126.36 MiB（132,497,408 bytes＝配置面積 33,124,352 px × 4バイト）に、5 MiB 単位への切り上げによる余裕 3.64 MiB（3,817,472 bytes、+2.9%）を加えた値。余裕は最大寸 512px タイル（196,608 px × 4 = 786,432 bytes）約 4.8 枚分に相当し、将来の 512px 級の小幅な追加（数棟）を再承認なしで吸収できる程度の幅である。切り上げ規則（5 MiB 単位）は再現可能で、将来のミックスにも同じ規則を適用できる。
- 測定方法: アトラス画素数（配置面積）× 4バイト、mipmap なし。docs/plateau-hero-data.md §10.4 (ii) と同一の式である。再現は `tools/atlas-tiering-values.py`（配置表＋選定リストを入力とする）で可能で、本書の記録値をすべて assert で検証する。配置面積は配置表の 800 件から拡大なし規則で再計算し、長辺 128 での正確値 7,841,792 px が docs/plateau-hero-data.md §11 と完全一致することを確認済みである。

### 5.2 基準とする読み方の固定

新しい上限値の基準とする読み方は **(a) 配置面積×4バイト（mipmap なし）** に固定する。(b) シート全体の RGBA8 確保量と (c) mipmap 込みは参考値とし、上限の判定には使わない。理由は (1) (a) は docs/plateau-hero-data.md §10.4 (ii) と Issue #165 の測定方法の指定（Bolt 10 の GPU 試算の式と同一）と一致すること、(2) (b) は空きシート面積（S4 ミックスの充填率 0.6581）を数え、(c) はさらに mipmap 分を数えるため、長辺 256 のみのアトラスでも (b) 128.00 MiB・(c) 170.67 MiB となり 102MB を上回り、従来の A2 受入（§11.3 で (b) 64.00 MiB・(c) 85.33 MiB が内側として受入）と整合しないこと、である。(a) を基準とすることで、全 256（87.45 MiB）は旧天井の内側、S4 ミックス（126.36 MiB）は新しい上限値 130 MiB の内側、という一貫した判定になる。

### 5.3 射程と留保

- 本提案は Epic #138 への記録をもって行い、実施は別単位とする（2026-11-12 所有者決定の射程 (2) の手順）。docs/verification-criteria.md の天井値は本 PR では変更しない（構造上限 totalNodes 4046・programs 45・geometries 683・textures 88・usedJSHeapSizeMB 102 は変更しない）。usedJSHeapSizeMB 102 自体も変更しない。新しい 130 MiB はヒーロー圏アトラスの GPU 試算（読み方 (a)）だけの上限値であり、JS ヒープの実測値の上限ではない。
- S4 ミックスのインライン模型での HTML 合計は中央値で §10.4 (i) を 461,990 bytes 上回るため、実施は外部化（R5-3d、#164 の設計）を前提とする。外部化模型では HTML は 8,128,518 bytes となり (i) を満たす。視覚受入は #143 へ送る。
- 新しい上限値の適用範囲はヒーロー圏のテクスチャ解像度と GPU／heap 試算のみで、全域への例外拡大はしない。

## 7. フォールバック条件（512px 級の絞り込み）

512px 級を広げて新しい上限値 130 MiB を超える場合、または実施時の条件が変わった場合の絞り込みとフォールバック条件を定める。絞り込みの順序は次のとおり（上から順に外す）。

1. 面積基準（フットプリント 1,500 m2 以上）を外す。残りは天守＋高さ 45 m 以上（S3、49 棟）。
2. 高さのしきい値を 45 m から 50 m へ上げる。残りは天守＋高さ 50 m 以上（S2、23 棟）。
3. 高さ基準を外す。残りは天守のみ（S1、1 棟）。
4. 天守も外す（全 256px 級。A1 の正確値）。

- 256px 級へのフォールバック: 512px 級から外れた棟は 256px 級へ戻す。256px 級より下（128px 級）へは落とさない。全 256 の GPU 試算 (a) 87.45 MiB は旧天井の内側であり、HTML 合計（置き換え）14,060,662 bytes も §10.4 (i) の内側であるため、256px 級は常に安全なフォールバック先である。
