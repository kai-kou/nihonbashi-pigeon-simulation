# 開発手順: ソース分割とビルド

このリポジトリは二本立てである。編集するソースは `src/` に分割して置き、配布する単一 HTML（ルートの `index.html`）はビルドで生成する。単一 HTML 成果物はこれまでどおり残る。

## 正本と生成物

- **正本はリポジトリの `src/` のみ**である。ルートの `index.html` は生成物であり、**手編集しない**。生成物への直接編集は次のビルドで失われ、レビューもできないため禁止する。
- アーティファクト側のソース（ビルダーが扱う単一 `index.html` と `assets/`）は作業コピーであり、正本ではない。アーティファクト側と `src/` の両方を正本として並行編集しない。同期は必ず下記の手順で一方向ずつ行い、同期のたびに `src/` 側へ寄せる。
- アーティファクト側の変更をルート `index.html` へ直接コピーする経路は廃止した。リポジトリへの反映はすべて `src/` ＋ビルド経由とする。

## 分割構成

| ファイル | 内容 | 編集の目安 |
|---|---|---|
| `src/template.html` | HTML 本体（マークアップ、タグ骨格、各パートへの参照トークン） | 画面要素・文言はこちらと、該当パートの組み合わせで変更する |
| `src/style.css` | `<style>` の内容（258 行） | 見た目はこちら |
| `src/scripts/webfont.js` | Web フォント読み込み（6 行） | — |
| `src/scripts/build-city.js` | 都市の構築（1,932 行）: レンダラ初期化、街・街路小物・近距離レイヤー・屋上レイヤー | 街側の変更 |
| `src/scripts/pigeons.js` | ハトの構築と個体更新（2,253 行） | ハト側の変更 |
| `src/scripts/simulation.js` | 時計・季節天候、カメラ、遮蔽、品質、C6/C7、操作、UI、メインループ、QA フック（1,831 行） | システム側の変更 |
| `src/scripts/perf-panel.js` | 性能計測パネル（202 行） | 計測表示の変更 |
| `src/data/citygeo.js` | `window.CITYGEO = ...;`（都市ジオメトリのデータ、1 行） | データであり手編集しない |
| `src/assets/three.min.js` | Three.js r128（vendor、603,445 bytes） | 手編集しない。世代移行時はファイル差し替え＋再ビルドで行う |
| `src/assets/city.js` | `window.CITY = ...;`（OpenStreetMap 由来の都市データ、631,567 bytes） | データであり手編集しない |

ビルドスクリプトは `tools/build.py`（Python 標準ライブラリのみ、乱数・時刻・ネットワーク不使用）。

## ビルドと検証

```sh
# src/ からルート index.html を生成する
python3 tools/build.py build

# 決定論と整合の検証: 2 回生成してバイト一致することと、
# ディスク上の index.html が再生成結果と一致することを確認する
python3 tools/build.py verify

# 期待する git blob が決まっている場合は照合できる
python3 tools/build.py verify --expected-git-blob <sha>
```

`verify` が失敗したら、生成物をコミットしない。原因が `src/` の意図した変更で説明できない場合は、現行の単一 HTML を維持し、Issue に記録する（X4 の停止条件）。

各パートファイルは末尾の改行をちょうど 1 つ持ち、ビルドは埋め込み時にその 1 つを取り除いてテンプレートへ差し込む。この規約により、分割前とバイト単位で同じ生成物が得られる。

## 同期手順 A: ビルダー経由の変更をリポジトリへ取り込む

アーティファクト側（ビルダー）で編集・ビルドされた変更は、次の手順で取り込む。

1. アーティファクト側の成果一式（単一 `index.html` と `assets/three.min.js`、`assets/city.js`）を取得する。この単一 `index.html` は配布形式ではなく、外部 script 参照のままのアーティファクト形式であること。
2. 再分割する。

   ```sh
   python3 tools/build.py split --from <アーティファクト形式 index.html のパス> --assets <assets ディレクトリ>
   ```

   `split` は `src/` を再生成した後、再ビルドしたアーティファクト形式が入力とバイト一致することまで自動で検証する。一致しなければエラーで止まる。
3. `python3 tools/build.py build` と `python3 tools/build.py verify` を実行する。
4. 差分を確認する。`src/` の差分が取り込む変更の範囲と一致すること、生成物 `index.html` の差分が同じ変更だけであることを確認し、`src/` と `index.html` を同一の PR に含める。

## 同期手順 B: リポジトリ側の変更を公開へ戻す

`src/` を直接編集した変更をアーティファクト側で公開する場合は、先にアーティファクト側の作業コピーを最新の `src/` で置き換えてから、ビルダーの通常手順でビルド・公開する。古い作業コピーのまま公開しない。

1. `src/` を編集し、上記の `build` と `verify` を通す。
2. アーティファクト形式の単一ファイルを書き出す。

   ```sh
   python3 tools/build.py artifact --out <アーティファクト側 index.html のパス>
   ```
3. `src/assets/three.min.js` と `src/assets/city.js` をアーティファクト側の `assets/` へバイト単位でコピーする（内容は配布形式でもアーティファクト形式でも同一）。
4. 書き出したファイルとコピーした assets が、`src/` から再生成したものとハッシュで一致することを確認してから、ビルダーでビルド・公開する。

## 決定論

同じ `src/` からは何度ビルドしても同じ `index.html` が得られる（`verify` が毎回確認する）。生成物に時刻や乱数が混入する変更は入れない。`split` も冪等であり、同じ入力からは同じ `src/` が再生成される。
