## 1. 現行方式の整理

- `tools/build.py` は `<!-- @include-base64 data/texture-atlas.jpg -->` トークン
  （`ATLAS_B64_RE`）を検出し、dist／artifact の両モードで
  `src/data/texture-atlas.jpg` を base64 データ URI としてインライン化する。
  出力行は `window.TEXTURE_ATLAS = "data:image/jpeg;base64,..."` の 1 行で、
  行全体は 2,973,946 bytes（base64 本体 2,973,876 bytes＋前後 70 bytes）。
- `src/template.html` 345 行目がそのトークン行である。
- `split` は同行を検出して base64 を復号し `src/data/texture-atlas.jpg` へ戻し、
  テンプレートへトークン行を復元する。`atlas_seen` の assert がある。
- 消費側は `src/scripts/build-city.js` hero パス（805〜837 行目）で、
  `new Image()` を作り `heroAtlasImg.src = window.TEXTURE_ATLAS` とする。
  onload でのみ `needsUpdate` を立て、encoding は sRGBEncoding、anisotropy 8、
  マテリアルは facadeParams と同一プロファイルで map だけを差し替える。
- 重要な帰結: 消費側は `window.TEXTURE_ATLAS` を「URL 文字列」として扱っており、
  data URI か相対 URL かを区別しない。外部化は値の差し替えで足り、
  消費側の読み込みコードの変更は要らない。

## 2. 配置

- 採用する置き場: 公開アーティファクト（artifact 形）の `assets/texture-atlas.jpg`。
  すなわち配信版の index.html と同じディレクトリにある `assets/` 配下で、
  既存の外部ファイル `assets/three.min.js`・`assets/city.js` と同列に置く。
- 採用の理由: artifact 形では 2 本のアセットスクリプトがすでに `assets/` 配下の
  外部ファイルとして配信されている実績があり、`assets/` は実証済みの
  外部ファイル配信経路である。アトラスを同経路に載せるのが最も検証済みの
  置き方である。
- リポジトリ側の正本は `src/data/texture-atlas.jpg` のままとし、artifact 形への
  配置物はその派生コピーとする。派生コピーは SHA-256（`cc45c0d0…`）で
  正本と照合する。
- dist 形（リポジトリの index.html）は従来どおりインライン化を維持し、
  配置は変えない（§5 の分離境界を参照）。

## 3. 参照

- 採用する参照方法: `window.TEXTURE_ATLAS` の値を base64 データ URI から
  相対 URL `"assets/texture-atlas.jpg"` へ変える。artifact 形の出力行は
  `    <script>window.TEXTURE_ATLAS = "assets/texture-atlas.jpg";</script>`
  （71 bytes）とする。
- `build-city.js` の hero パスは変更しない。`heroAtlasImg.src` への代入、
  onload での `needsUpdate`、flipY 既定 true、sRGBEncoding、anisotropy 8 は
  そのまま通用する。
- 相対 URL は配信版ページと同一オリジン・同一ディレクトリ基準で解決される。
  新しいホスト・CDN・絶対 URL は使わない（外部ホスティング依存とコストを
  持ち込まない）。
- HTML からの差し引き: artifact 形の HTML はアトラス行が 2,973,946 bytes から
  71 bytes になり、2,973,875 bytes 減る。外部ファイルは 2,230,406 bytes を
  別途配信する。dist 形の HTML 合計は変わらない（11,102,394 bytes のまま）。

## 4. build.py の経路（インライン化トークンからの分離方法）

テンプレート行は変えず、`build_bytes(mode)` のアトラス分岐をモード依存にする。
本 Bolt は設計のみで、実装は後続単位が行う。実装単位への要求仕様は次のとおり。

- `build_bytes("dist")`: 現行どおり。`ATLAS_B64_RE` 行を検出して base64 を
  インライン化する。`cmd_build`・`cmd_verify` の挙動は変わらない。
- `build_bytes("artifact")`: 同じトークン行を検出したら、インライン化せず
  新規定数 `ATLAS_URL_LINE`
  （`    <script>window.TEXTURE_ATLAS = "assets/texture-atlas.jpg";</script>`）
  を出す。トークン行そのものはテンプレートに残し、両モードの分岐点は
  build.py 内に 1 か所だけ作る。
- `cmd_artifact`: artifact 形 HTML の書き出し後に `src/data/texture-atlas.jpg` を
  出力先ディレクトリの `assets/texture-atlas.jpg` へ複写する（`assets/` が無ければ
  作る）。複写後にサイズと SHA-256 を表示し、正本の SHA-256（`cc45c0d0…`）と
  一致しなければビルドを失敗させる。
- `cmd_split`: URL 行（`ATLAS_URL_LINE`）もアトラス行として認識する。
  data URI 行の場合は従来どおり base64 を復号して復元し、URL 行の場合は
  assets ディレクトリの `texture-atlas.jpg` を読み `src/data/texture-atlas.jpg` へ
  書き戻し、SHA-256 を照合する。いずれの場合もテンプレートへトークン行を復元し、
  `atlas_seen` の assert を満たす。再ビルド検証（artifact 形のバイト同一、
  dist 形のバイト同一）は従来どおり行う。
- 決定論性: URL 文字列に時刻・乱数は含まず、artifact 形 HTML は同一 src/ から
  常に同一バイトになる。アトラス JPEG は複写のためバイト同一である。

## 5. 分離境界

- 単一 HTML のまま残すもの: アプリ本体（template.html・スクリプト・スタイル）と
  データ（`data/citygeo.js`・`data/citygeo-hero.js`・`data/city-hero-buildings.js`）。
  dist 形の index.html は引き続き単一ファイルである。
- 外部に出すもの: テクスチャアトラス（`src/data/texture-atlas.jpg`）のみ。
  しかも artifact 形（配信版）に限る。D5 改訂の射程はこの範囲であり、
  アプリ本体・データの外部化は行わない。
- 例外の射程: 本方式は 2026-11-12 所有者決定の射程 (1)（アトラスのみ外部ファイル化）
  の内側である。ヒーロー圏以外のテクスチャ・全域への例外拡大はしない。
  新しい上限値の提案は本単位では行わず、R5-3e（#165）の対象とする。

## 6. 方式 (b) img 要素の再検討

Bolt 第13回は方式 (b) img 要素を「DOM への画像要素の追加と artifact 形での
外部ファイル参照の扱いが要るため」却下した。本 Bolt で D5 改訂を前提に再検討した。

- 再検討で変わった点: 外部ファイル参照の扱いは、`assets/` 配下の 2 本の
  アセットスクリプトがすでに artifact 形で外部参照されている実績により、
  外部ファイル一般としては解決済みである。したがって却下理由の後半は、
  外部ファイルそのものについては成立しなくなった。
- それでも (b) を採用しない理由: 消費側はすでに JS 内で `new Image()` を作って
  URL 文字列から読み込んでおり、DOM へ `<img>` 要素を置く必要がない。
  DOM 要素を追加すると、配置・可視性の管理（非表示化）と、DOM 画像と
  THREE.Texture 用画像の二重の読み込み経路（別々に読むか `tex.image` へ
  結び付けるか）の設計が新たに要る。URL 文字列方式は同じ配信を DOM ノードの
  追加なしで達成でき、(b) に機能上の利点がない。
- 結論: 方式 (b) img 要素は引き続き却下する。

## 7. 採用方式の決定

- 採用方式: (a') URL 文字列定数。`window.TEXTURE_ATLAS` の仕組みは Bolt 第13回の
  方式 (a) data URI 文字列定数と同じで、値だけを base64 データ URI から相対 URL
  `"assets/texture-atlas.jpg"` へ変える。配置は artifact 形の `assets/` 配下。
- 却下した代替案:
  - (b) img 要素: §6 のとおり。DOM ノードの追加と二重の読み込み経路が要り、
    URL 文字列方式に対する利点がないため却下。
  - base64 を `src/data/citygeo-hero.js` へ直接埋め込む方式: Bolt 第11回で却下済み。
    約 2.97MB のテキストを形状データの生成ツールへ結合させるため却下。
  - 絶対 URL・別ホスト・CDN: 新しいホスティング依存とコストを持ち込むため却下。
    同一オリジンの相対 URL のみを用いる。
  - ルート直下の兄弟ファイル（配信版 index.html と同じ階層の `texture-atlas.jpg`）:
    artifact 形での実績がない新しい配信経路のため不採用。`assets/` での配信が
    実測で不成立だった場合の代替候補（フォールバック候補 F-2）として残す。
  - タイル別・複数シートへの分割: 階層化の具体値は R5-3e（#165）の対象であり、
    本単位の範囲外のため採用しない。単一 4096px シート A2 のまま外部化する。
  - インライン継続（現状維持）: 採用方式が成立する限り採用しない。成立しない場合の
    フォールバックとして残す（§9）。

### 8.3 結論（プラットフォーム層）

  フォールバック F1 へ倒れる条件には当たらない。
- 本結論の射程はプラットフォーム層の配信可否に限る。`space` の配信版への具体的な

### 8.4 留保 — コーディネーター側の独立した実ブラウザ再確認は未実施

- コーディネーター自身による独立した実ブラウザ再確認は未実施である。

### 8.6 実測計画と合格条件（本 Bolt の設計として固定）

- M1（配信）: テスト用アーティファクトに `assets/texture-atlas.jpg` を置き、
  公開経路から取得して HTTP 200 であること、バイト数が 2,230,406 bytes で
  SHA-256 が `cc45c0d0…` と一致すること。
- M2（読み込み）: 実ブラウザで配信版を開き、アトラス URL の読み込みが完了する

  G4 により、対象領域が主要視点で描画されていることのスクリーンショット目視を

  なお、G4 の主要視点での目視は本実測では未実施であり、§8.5 手順 3／#143 へ委譲される（§8.2 の限定付き「M2 成立（読み込み完了の範囲で）」と整合する）。

- 合格: M1・M2 がともに満たされること。不成立の場合は不成立の証拠と理由を記録し、

## 9. フォールバック条件

外部化できない場合にインライン継続へ戻る条件と判定値。フォールバック時の HTML 合計は
現行 main を起点に §10.4 の判定値と照合する。

- F1（配信不成立）: §8 の M1 または M2 が証拠つきで不成立の場合、外部化を実施せず
  インライン継続とする。実装単位は build.py を変更しない。
- F2（代替配置の試行）: `assets/` での配信が不成立の場合、ルート直下の兄弟ファイル
  への配置を代替候補として 1 回だけ試す（§7）。それも不成立なら F1 へ倒れる。
- F3（HTML 合計）: フォールバック時の HTML 合計は現行 main の 11,102,394 bytes で、
  §10.4 (i) の 15,000,000 bytes 以下を満たす。余裕は 3,897,606 bytes。
- F4（GPU 試算）: Bolt 第11回の正確値 29.91 MiB（31,367,168 bytes）が §10.4 (ii)
  の 102MB 以下を満たす。シート全体 RGBA8 64.00 MiB、mipmap 込み 85.33 MiB も
  102MB の内側である。
- F5（textures）: 増分 +1（73→74、合計 88 以下）が §10.4 (iii) を満たす。
- F6（視覚受入）: §10.4 (iv) は未確認のまま #143 へ送る。フォールバック時も同じ。
- F7（階層化による将来の超過）: R5-3e（#165）で階層化の具体値が決まり、新しい上限値を
  実測根拠つきで Epic #138 へ記録してから実施する。将来のアトラスが (i)(ii)(iii) の
  いずれかを超える場合は、インライン A2 へ戻るか、形状のみ＋手続きファサードへ
  フォールバックする（§10.4 の判定に従う）。
- 注記: Bolt 第10回の推定値（HTML 合計 約 9,690,306 bytes、GPU 試算 33.16 MiB）は
  推定であり、判定には使わない。判定に使う正確値は Bolt 第11回の値（§0 参照）と

## 10. 実装単位への申し送り
