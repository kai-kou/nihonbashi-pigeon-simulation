## 左右交互ステップの検証記録（項目 7 の残件）

交互ステップだけは、以下の 4 回の条件変更でも路面視点では読み取れませんでした。

1. **接写フォーカス（×10）**: 対象個体がテレメトリの採餌表示に反して速度 0 km/h で留まり続け、ステップ自体が発生しない。
2. **フォーカスなし・路面視点（×10、餌まき 3 回）**: 歩行と歩行中の鮮やかな赤い脚は確認。距離約 10〜11 m・両脚同色・奥の脚が体の陰になるため、交互の読み取りはできず。
3. **低速のつもりが条件不成立**: 当時ビルドの速度 UI に ×1・×2 がなく ×60 での観察となり、距離約 18〜21 m では脚は点状。
4. **×1・×2 追加後の最終再確認（路面視点、フォーカスなし、餌まき 3 回）**: マル・ミケ・トワの 3 羽が約 9〜14 m で歩行。赤い脚 2 本は確認できたが、脚が数ピクセルで左右・前後の区別がつかず、脚の重なり・体の陰・餌粒の遮りがあり、歩行自体もその場の小刻みな採餌中心で横方向の連続歩行が現れなかったため、左→右→左の交互は読み取れず。

2026-10-31、所有者の判断により、項目 7 は「色・太さ・歩行は確認済み、交互ステップは路面視点の観察条件の限界」として閉鎖しました。これはモデルの欠陥の認定ではなく、ステップ実装が無いことの証拠でもありません（実装自体はソースと QA スナップショットで確認済み）。

## R1-1 首虹色の視角依存シフト（Issue #67）

- 目的: 現行の首はグラデーション texture＋fresnel sheen＋視線方位係数で駆動されているが、構造色が視線方位のみに依存し光源方向を無視していたため、カメラ固定で個体が太陽に対して向きを変えても色が流れない状態だった。これを解消する。
- 変更内容: 既存の首 sheen シェーダ（`src/scripts/pigeons.js` の `makeNeckSheenMat()`）に太陽方向 uniform `uSunDir` を追加し、half-vector の NdotH で hue mix 係数 `t` を `(ndh-0.5)*0.35`（±0.175 の範囲）だけ変調した。テクスチャ回転は現行維持で、変更は既存 ShaderMaterial の式拡張のみ。太陽方向は `src/scripts/simulation.js` の `updateSkyEnv()` で既存の `_sunDir`（Sky ドームと同一、季節・天候の太陽位置ロジック由来）を各鳥の既存 neck sheen マテリアルへ毎フレーム複写するもので、新規の太陽計算系はない。プログラム・ノード・テクスチャの追加はなく、静的サイト数は ShaderMaterial 9→9、Mesh 84→84、CanvasTexture 28→28、Geometry 95→95（いずれも +0）。
- ビルド: `tools/build.py` で再生成。4,908,323 bytes、git blob `e89d38a9974bb6457d3b37d02691dc72117a1f10`、SHA-256 `20f1c80faa2b9b563ed11258304d99fb422bb838bd9f0857358a4c8d038e2024`、決定論的再ビルド一致、inline script 6 本の `node --check` 合格。
- 受入への対応見込み: 至近（2〜5 m）でカメラ角を変えたとき、首の色が緑〜紫方向へ連続変化する設計。計測パネルでの programs・totalNodes +0 は静的差分で確認済みだが、ランタイムの確定計測（計測パネル値、最悪条件のフレーム時間 520 ms 内）は検証バッチで行う。
- 専門レビューによる追加受入観点の訂正: グルーミング反映コメントの「カメラ固定で個体が頭を振る場面」は、首シェルが体幹グループ bodyG の子で headG の回転が及ばない機構のため、文字通りには成立しない。検証バッチの試験は「カメラ固定・体幹 heading の変化」へ訂正し、Issue #67 へ訂正コメント 6569813919 を記録した。Issue #67 本体の受入条件（カメラ角を変えたときの連続変化）は変更しない。太陽項単独の確認には、同一 heading・同一カメラで太陽幾何だけを変える差分試験（停止または ×1）を検証バッチで用いる。逆光の degenerate case（L+V のゼロ正規化）へのガードは提案として次回以降の同シェーダ改修へ申し送る。
- 視覚受入: 未確認。実ブラウザ目視は検証バッチ（R4-1）へ送る。

## R1-2 足の形状と色の実体化（Issue #68、外観監査 A3）

- 目的: 現行の基本脚は MeshBasicMaterial の平らな赤で、至近・路面視点で脚が色の帯にしか読めず、鱗の立体感がなかった。脚の太さ・色は 2026-10-31 改善で到達済みのため、本単位の主眼は無陰影の平坦さの解消（陰影・鱗感）である。グルーミング反映コメント 6568213360 に従う。
- 変更内容: `src/scripts/pigeons.js` のみ、3 か所（脚以外のマテリアル・形状には触れていない）。
  1. SHARED_LEG_MAT を MeshBasicMaterial から MeshStandardMaterial へ変更。色は純赤 0xea0d0d を維持し、roughness 0.6（隣接する角質系の既存値＝嘴 0.55・眼環 Hi 0.6 と整合）を選んだ。脚の位置・形状・オフセット計算は変えていない。
  2. 鱗状の横縞を描いた共有テクスチャ `legScaleTex`（手続き生成の CanvasTexture 128×128、外部素材なし）を新規作成し、基本脚（tarsus）に bumpMap として流用した（bumpScale 0.02、P5 の翼 barb 細線と同じ値）。円筒 UV の u が周方向・v が高さ方向のため、横縞は 16 px ごとに暗い溝＋明るい稜線の 8 段とし、 faint な縦 seams を加えて鱗の区切りとした。データテクスチャのため sRGB エンコーディングなし。共有 1 枚のみで個体ごとに増やさない。同一共有マテリアルを使う足板・足首球にも同じ bump が及ぶ（マテリアルを分割しない最小変更のため）。
  3. 至近 toe の SHARED_TOE_MAT の emissiveIntensity を 0.85 から 0.35 へ適正化した。色（0xe80d0d）・emissive 色（0x7a0404）は変えていない。
- D1 厳守: 歩行の足運び・タイミング・ステップ関連コード（pigeons.js の stepping 周り、脚の位置・オフセット計算）には一切触れていない。差分は上記 3 か所のみで、stepping ブロックの差分はない。
- ビルド: `tools/build.py` で再生成。4,910,708 bytes（変更前 4,908,323 bytes、+2,385 bytes）、git blob `f7d0f1ad0c4bb4e34899e603be0cf66bf2262476`、SHA-256 `a754645b204ad7acb5b1d49bcecdddb547421566238c30321fd2d2f387b898bc`、決定論的再ビルド一致（`tools/build.py verify` 合格）、inline script 6 本の `node --check` 合格。
- 静的計測（変更前 → 変更後、grep ベース）: pigeons.js の Material  ctor は MeshBasic 9→8・MeshStandard 31→32（総数 43→43、+0）、CanvasTexture ctor は pigeons.js 9→10・全 src/scripts 28→29（+1、共有 1 枚のみ）、Geometry ctor は pigeons.js 47→47（+0、新規メッシュ・形状なし）。構造上限との照合（docs/verification-criteria.md）: totalNodes は新規メッシュなしのため静的 +0、geometries +0、textures は静的 +1 で上限 88 の内側、programs は下記の静的判断を参照。
- programs への静的判断（ランタイム確定値は検証バッチで計測）: 既存シーンに「Standard＋bump のみ（map・roughnessMap・vertexColors・normalMap なし）」の組み合わせは存在しない。既存の bump 使用はすべて map＋roughnessMap 付き（体・翼・尾・首 Physical）であり、色のみの Standard とも異なるため、脚の新バリアントは静的には新規プログラム +1 の見込みである。Basic プログラムは眼・瞳孔・眼環など他の Basic マテリアルが残るため消えない。したがって +0 の成立条件は静的には満たさない見込みで、2026-11-01 時点の到達点 programs 42 から 43 への見込みとなり、上限 45 の内側ではある。検証バッチで計測パネルの programs を読み、43 以下（上限 45 内）であることを確認すること。+0 を厳密に求める場合は、体と同じ map＋roughnessMap 付きの組み合わせに寄せる設計変更が必要になるが、拡散色の見え方が仕様外に変わるため本スプリントでは行っていない。スプリントレビューでの判断事項として申し送る。

- キャップ越しの見え方についての判断: 移動するハイライトの主因はキャップ側（clearcoat＋環境マップ、opacity 0.25 の透明シェル）で、視点移動に伴いハイライト位置が動く構造は既にある。虹彩 roughness を 0.08 へ下げると、キャップの下の虹彩自身のスペキュラがより鋭く・強くなる。キャップの opacity は 0.25 と薄いため虹彩は覆い隠されず、虹彩のグラデーション模様は読めたまま、鋭い二次的な光沢が重なってハイライトの移動が判別しやすくなる設計である。瞳孔の扁平化は出っ張った玉感を抑えつつ、位置の外側移動で黒中心の突出（変更前と同等）を保ち、眼球表面上の円盤として読ませる。眼環をよりマットにすることで、光沢のある眼球と粉質の眼環のコントラストがつき、P6 の目・嘴・眼環の判別が保たれる設計である。
- 白飛びリスクについての所見: リスクは低いと判断する。理由は (a) キャップは opacity 0.25・envMapIntensity 0.3 と P6 で控えめに設計されており、本単位はキャップ側を強めていない、(b) 虹彩は無地の白ではなくグラデーションの irisTex マップ付きで、拡散輝度は上がらない（roughness 低下はスペキュラの鋭さ・強さのみに効く）、(c) 拡散光の増加や emissive の追加は一切ない、(d) 瞳孔はほぼ黒（0x0d0a08）のままで眼の中心の暗さが残り、眼環はよりマットになるため、眼全体が白く抜ける方向には働かない。ただし強い直射光の角度では眼球上に小さな鋭いスペキュラ点が出る可能性があり、個体ごとの白飛びの有無は実ブラウザ目視で確認する（下記「視覚受入」参照）。
