## 目的

品質向上プログラム（計測基盤、街の PBR、鳩の模様・LOD）が作った土台の上で、「見た目と動きが実物にどれだけ近いか」を一段上げる。伸ばしどころは次の3観点である。

1. 外観: 首の虹色と足の質感、羽毛の艶、個体差の残り。（注: 2026-10-31 の目視で「平坦なミント色パッチ」「細いオレンジ色の線」と観察されたのは 2026-10-30 改善ビルドの状態で、2026-10-31 の検証基準の基準状態では首（項目6）は確認済み、脚の色・太さも確認済みである。R1-1・R1-2 の残課題は、外観監査で確定した光源連動化と陰影・鱗感である。スコアカードのベースライン処分を正とする。）
2. 行動: 頭部運動、採餌、離着陸、群れ、静止時の微動。歩行の足運びは D1 で閉鎖済みのため対象外。
3. 環境・光: 影の柔らかさ、大気の奥行き、濡れ・きらめき、ファサードの経年変化。

## 前提（D1〜D6 の継承と追加前提）

- D1: 左右交互ステップの閉鎖は再開しない。歩行の足運び・タイミングには触れない。
- D2: PLATEAU は主軸にしない（X3 はゲート不通過で閉鎖済み。再提案しない）。
- D3: 性能予算が不足する場合は街側を優先し、重い行動系単位を繰り延べる。
- D4: Three.js r128 のまま進める。世代移行と混ぜない。
- D5: 成果物の単一 HTML を維持する。
- D6: テクスチャは手続き生成のみとする。外部素材・写真素材は使わない。
- 追加前提1: 性能天井（docs/verification-criteria.md の6条件と構造上限）はリアリティのために引き上げない。超過する変更はマージしない。
- 追加前提2: ベースラインのない単位は、着手前に現行ビルドの Before を記録する。改善の主張は Before／After の組でのみ行う。
- 追加前提3: kaikou へはアウトカムの報告のみで、承認・確認は求めない（2026-11-02 所有者指示）。公開反映（R4-2）を含む全スプリントは承認なしに継続し、判断が割れる事項は Issue に記録して進める。
- 追加前提4: 進め方は docs/ai-dlc-bolt.md に従う。本書の単位・完了条件・D1〜D6 は変更しない。

## フェーズ

既存の品質プログラム検証バッチ（Issue #7〜#31 の受入判定）と並行して、リアリティ専用の物差しを作る。

### R1: 外観のリアリティ

- R1-1: 首虹色の視角依存シフト（視角で緑〜紫へ連続変化する虹色）。
- R1-2: 足の形状と色の実体化（立体形状と赤系の色。足運びには触れない）。
- R1-3: 羽毛の微細変調（斜光の艶と羽方向の読み）。
- R1-4: 個体差の第3層（模様シード・体格・姿勢の癖）。
- R1-5: モーフ模様の実体化・第2弾（外観監査 A2 で追加。checker のチェック模様、pied の白斑、モーフ配分の実在化）。
- R1-6: 眼の角膜光沢（外観監査 A4 で追加。ノード・ジオメトリを増やさないパラメータ変更で視点連動ハイライトを出す）。
- R1-7: 首テクスチャ共有化（外観監査 A5 で追加。個体ごとの複製をやめ、テクスチャ予算を20以上回収する）。

入口条件: 各単位の対象領域について Before が記録されていること。

### R2: 行動のリアリティ

- R2-1: 頭部運動の生体化（保持相と突き出し相の非対称タイミング。頭・首のみ）。

- R2-3: 離着陸遷移の実体化（離陸の沈み込み、着陸のフレア）。

- R2-5: 静止時の微動（羽繕い・瞬き・尾の動き）。
- R2-6: 頭のサッケードと注視パターン（行動監査 提案5 で追加。角速度制限つきサッケード＋注視保持、警戒・着陸前確認の姿勢）。

完了条件: R1 と同じく、Before／After がスコアカードに記録されていること。足運びへの変更が含まれていないことが全単位の共通条件。

## 運用（3時間ごと Bolt）

- 3時間ごと1回（cron pigeon-realism-sprint）、有限単位を1つだけ進める。1回の実行を Bolt と呼び、種別は Inception／Baseline／Construction／Operations／Continuation の5種とする。単位ごとに専門チーム（実装担当、実装者と異なる専門レビュー担当、QA 担当）を組成し、コーディネーターが Approver として Bolt の合否とマージ可否を最終判定する。
- 流れ: 対象単位の claim（開始時刻・範囲・完了条件・担当構成・Approver を明記）→ Inception 退出チェック E1〜E7 の実施（いずれかが欠ける Unit は Construction に進まない）→ ベースライン確認 → 実装（作業ブランチ、新規ブランチは `bolt/` 接頭辞）→ PR 作成 → セルフレビュー → 専門レビュー → 指摘の修正（ブラッシュアップ）→ Approver 判定（受入条件の1件ずつの照合）→ 計測可能な条件を満たし性能天井内ならマージ。満たさなければ PR を開いたまま、ブロッカーと次の手を Issue に記録する。
- WIP 上限: 未判定の PR と受入待ちの合計が2件に達したら、新規 Construction Bolt を開始せず Operations（検証）Bolt を優先する。
- G3 ロック: 同一描画領域の視覚未確認がある間は、その領域の後続 Unit を開始しない（Inception 時点から効かせる）。
- 完了規律: 有限の成果物（マージされた PR、受入判定の根拠になる新規証拠、リファインメントで ready になった Issue 群、配信確定の実測結果）がない反復は Bolt として完了しない。同一条件の再確認だけの実行は Bolt に数えず、確認記録のみを残す。
- 実ブラウザ目視が要る視覚受入はスコアカード検証バッチへ送り、その旨を PR と Issue に明記する。未確認を「確認済み」と書かない。
- 前回 Bolt の PR が未マージで残っている単位は、完了まで継続し、新規単位と並行させない。
- 報告はアウトカムベース（何が見て分かるように変わったか、証拠、未達と理由）で、7:00–20:00 は毎時定時報告の枠組みに載せ、夜間分は翌 7:00 にまとめる。報告に承認・判断の依頼は含めない。
- 専門チームの監査（外観／行動／環境・性能の3専門）は 2026-11-02 にすべて完了し、バックログへ反映済み（グルーミング）。子 Issue は当初の16件に監査追加6件（#83〜#88）を加え、さらに R4-3 #114・R4-4 #119・R4-5 #121・R4-6 #126 の追加により 26件。programs の配分ルール（プログラム全体で新規 +2 以内、+1 は予備）は全体 Epic #82 のコメントに記録した。

## 進捗率の定義

全体進捗報告で用いる進捗率の定義は次のとおりとする（定義を変える場合は変更理由とともに本書を改訂する）。

- 分母: realism 子 Issue の総数。基準時点（2026-11-02）で 22 件（R0: #66、R1: #67〜#70・#83〜#85、R2: #71〜#75・#88、R3: #76〜#79・#86・#87、R4: #80・#81）。子 Issue が増減したら新しい総数を分母にする（例: R4-4 #119 の追加後は 24 件、R4-5 #121 の追加後は 25 件、R4-6 の追加後は 26 件）。
- R4-6 の分解単位（R4-6a〜d）は R4-6 の内訳であり新規スコープではないため分母に含めない。分母は 26 のまま（R4-6 を 1 件として数える）。
- 実装進捗率 = （closed の子 Issue 数 + 実装受入済みの子 Issue 数）/ 分母。実装受入済みとは、対応 PR がマージ済みで、視覚・ランタイム受入が検証バッチ送りのため Issue が open のままのものをいう（スプリントの記録と Issue コメントで判定する）。
- 完全完了率 = closed の子 Issue 数 / 分母。
- Epic 別（R0〜R4）にも同じ定義で内訳を出す。
- 率には必ず分子・分母の件数を併記する。
