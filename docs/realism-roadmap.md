# リアリティ向上ロードマップ

2026-11-02 制定。所有者指示（2026-11-02）「よりリアリティを高めるための計画を専門チームでロードマップ、エピック、Issue にまとめ、達成までの間、毎時スプリント開発を実行する。スプリントごとに PR 作成、セルフレビュー、スプリントレビューし、ブラッシュアップできたらマージ、結果はアウトカムベースで報告する」に基づく実施計画。

## 目的

品質向上プログラム（計測基盤、街の PBR、鳩の模様・LOD）が作った土台の上で、「見た目と動きが実物にどれだけ近いか」を一段上げる。伸ばしどころは次の3観点である。

1. 外観: 首の虹色（2026-10-31 の目視確認で未確認: 平坦なミント色パッチで色変化なし）、足（同: 細いオレンジ色の線）、羽毛の艶、個体差の残り。
2. 行動: 頭部運動、採餌、離着陸、群れ、静止時の微動。歩行の足運びは D1 で閉鎖済みのため対象外。
3. 環境・光: 影の柔らかさ、大気の奥行き、濡れ・きらめき、ファサードの経年変化。

## 前提（D1〜D6 の継承と追加前提）

- D1: 左右交互ステップの閉鎖は再開しない。歩行の足運び・タイミングには触れない。
- D2: PLATEAU は主軸にしない（X3 はゲート不通過で閉鎖済み。再提案しない）。
- D3: 性能予算が不足する場合は街側を優先し、重い行動系単位を繰り延べる。
- D4: Three.js r128 のまま進める。世代移行と混ぜない。
- D5: 成果物の単一 HTML を維持する。
- D6: テクスチャは手続き生成のみとする。外部素材・写真素材は使わない。
- 追加前提1: 性能天井（docs/verification-criteria.md の6条件と構造上限）はリアリティのために引き上げない。超過する変更はマージしない。
- 追加前提2: ベースラインのない単位は、着手前に現行ビルドの Before を記録する。改善の主張は Before／After の組でのみ行う。
- 追加前提3: 公開反映は R4-2 で所有者の承認を得てから行う。スプリントは公開行為を含まない。

## フェーズ

### R0: ベースライン確定とリアリティ・スコアカード

既存の品質プログラム検証バッチ（Issue #7〜#31 の受入判定）と並行して、リアリティ専用の物差しを作る。

- R0-1: リアリティ・スコアカードの策定（視点×観点の確認項目、確認方法、処分の基準、現行ビルドのベースライン処分）。

完了条件: スコアカードが文書として存在し、全視点・全観点にベースライン処分（確認／部分確認／未確認）が付いていること。

### R1: 外観のリアリティ

- R1-1: 首虹色の視角依存シフト（視角で緑〜紫へ連続変化する虹色）。
- R1-2: 足の形状と色の実体化（立体形状と赤系の色。足運びには触れない）。
- R1-3: 羽毛の微細変調（斜光の艶と羽方向の読み）。
- R1-4: 個体差の第3層（模様シード・体格・姿勢の癖）。

入口条件: 各単位の対象領域について Before が記録されていること。
完了条件: 各単位が受入条件を満たし、至近〜路面視点の Before／After がスコアカードに記録されていること。

### R2: 行動のリアリティ

- R2-1: 頭部運動の生体化（保持相と突き出し相の非対称タイミング。頭・首のみ）。
- R2-2: 採餌行動の多様化（ついばみの深さ・速さ・対象選択）。
- R2-3: 離着陸遷移の実体化（離陸の沈み込み、着陸のフレア）。
- R2-4: 群れの同期とばらつき（驚愕伝播、間隔変動）。
- R2-5: 静止時の微動（羽繕い・瞬き・尾の動き）。

完了条件: R1 と同じく、Before／After がスコアカードに記録されていること。足運びへの変更が含まれていないことが全単位の共通条件。

### R3: 環境・光のリアリティ

- R3-1: 影の柔らかさと環境光の反射（B5 の影スロットリング前提を壊さない）。
- R3-2: 大気の奥行き（距離ヘイズの校正。遠距離 LOD の判読を退行させない）。
- R3-3: 路面と川面の濡れ・きらめき増強（C6 の完了条件と重複させない増強分のみ）。
- R3-4: ファサードの経年変化と個体差（手続き生成の汚れ・色あせ・補修跡）。

完了条件: R1 と同じ。反射・影の追加コストが性能天井内であることが全単位の共通条件。

### R4: 統合受入と公開反映

- R4-1: Before／After スコアカード再計測と最終受入（性能6条件・構造量の再計測、品質プログラム検証基準への退行確認を含む）。
- R4-2: 公開反映と最終報告（公開は所有者承認を得てから）。

完了条件: 全項目に処分が付き、未確認は理由と次の手が記録されていること。公開反映は共有状態の読み戻しで確認すること。

## 運用（毎時スプリント）

- 毎時1回（cron pigeon-realism-sprint）、有限単位を1つだけ進める。単位ごとに専門チーム（実装担当、実装者と異なる専門レビュー担当、QA 担当）を組成し、コーディネーターがスプリントレビューを主宰する。
- 流れ: 対象単位の claim → ベースライン確認 → 実装（作業ブランチ）→ PR 作成 → セルフレビュー → 専門レビュー → 指摘の修正（ブラッシュアップ）→ スプリントレビュー（受入条件の1件ずつの照合）→ 計測可能な条件を満たし性能天井内ならマージ。満たさなければ PR を開いたまま、ブロッカーと次の手を Issue に記録する。
- 実ブラウザ目視が要る視覚受入はスコアカード検証バッチへ送り、その旨を PR と Issue に明記する。未確認を「確認済み」と書かない。
- 前回スプリントの PR が未マージで残っている単位は、完了まで継続し、新規単位と並行させない。
- 報告はアウトカムベース（何が見て分かるように変わったか、証拠、未達と理由）で、7:00–20:00 は毎時定時報告の枠組みに載せ、夜間分は翌 7:00 にまとめる。
- 専門チームの監査（外観／行動／環境・性能の3専門、2026-11-02 開始）の結果は、バックログの優先度と受入条件の具体化に反映する（グルーミング）。
